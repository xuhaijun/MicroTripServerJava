# 微旅途后端 · 数据库操作指南

> 面向日常开发的数据库实操手册：初始化、导入导出、删除、脏数据清理、数据清洗。
> 所有脚本基于本项目真实表结构（users / trajectories / trajectory_points），
> 在 MySQL 8.4 与 H2 上验证过语法（H2 差异单独标注）。
> 操作前必读 §10 安全规范——**先备份、先 SELECT 确认、再 UPDATE/DELETE**。

## 0. 表结构速览（写 SQL 前先看这个）

```text
users（用户表）
  id            varchar(64)  PK（如 u_9b7f42a77fe6a811145f1979）
  phone         varchar(20)  唯一，登录账号
  password      varchar(80)  BCrypt 哈希（不可逆，别想着明文找回）
  nickname      varchar(64)
  avatar        varchar(512)
  role          varchar(20)  USER / ADMIN
  created_at    bigint       毫秒时间戳

trajectories（轨迹主表）
  id            varchar(64)  PK（客户端生成的轨迹 id）
  user_id       varchar(64)  逻辑关联 users.id（无物理外键！）
  start_time / end_time / synced_at   bigint 毫秒时间戳
  distance      double       米（服务端契约单位！）
  duration      bigint       秒
  max_alt / min_alt / ascent / descent / avg_speed   double
  title / note / city
  points_json   TEXT         GPS 点数组（上限 20000 点，客户端协议键名是 pts）
  stops_json    TEXT         停留点数组（上限 500 条）

trajectory_points（轨迹 GPS 点表，逐点拆行存储）
  id            bigint       自增 PK
  trajectory_id varchar(64)  逻辑关联 trajectories.id
  seq           int          点序号
  lat / lng     double
  ts            bigint       毫秒时间戳
  alt / spd / acc 等 double
```

**三条铁律**：
1. 三表之间**没有物理外键**（JPA 应用层维护），删数据必须按
   `trajectory_points → trajectories → users` 顺序，否则留孤儿数据。
2. 单位契约：distance=**米**、duration=**秒**、时间=**毫秒**。清洗时别把单位改乱了。
3. `points_json` 是大字段，列表查询别 `SELECT *`（应用层已做投影，SQL 手工查同理）。

连接方式：

```bash
# MySQL（本机部署，见《本地环境运维手册》）
MYSQL="/c/Program Files/MySQL/MySQL Server 8.4/bin/mysql.exe"
$MYSQL -umicrotrip -pmicrotrip123 --default-character-set=utf8mb4 microtrip

# H2（默认文件库）：不能和应用同时打开；推荐用 H2 Shell
java -cp ~/.m2/repository/com/h2database/h2/*/h2*.jar org.h2.tools.Shell \
  -url "jdbc:h2:file:./data/microtrip" -user sa
```

## 2. 日常查询速查

```sql
-- 用户概况
SELECT COUNT(*) 用户数 FROM users;
SELECT phone, nickname, role, FROM_UNIXTIME(created_at/1000) 注册时间
FROM users ORDER BY created_at DESC LIMIT 10;

-- 每个用户的轨迹数与总里程（km）
SELECT u.phone, u.nickname, COUNT(t.id) 轨迹数,
       ROUND(IFNULL(SUM(t.distance),0)/1000, 1) AS 总里程km
FROM users u LEFT JOIN trajectories t ON t.user_id = u.id
GROUP BY u.id, u.phone, u.nickname ORDER BY 总里程km DESC;

-- 某用户最近 10 条轨迹
SELECT id, title, city, ROUND(distance/1000,2) AS km, duration,
       FROM_UNIXTIME(start_time/1000) AS 开始
FROM trajectories WHERE user_id = 'u_xxx' ORDER BY start_time DESC LIMIT 10;

-- 点数最多的轨迹（points_json 体积预警）
SELECT id, JSON_LENGTH(points_json) AS json点数,
  (SELECT COUNT(*) FROM trajectory_points p WHERE p.trajectory_id = t.id) AS 行表点数
FROM trajectories t ORDER BY json点数 DESC LIMIT 5;

-- 按时间段查（注意毫秒）
SELECT * FROM trajectories
WHERE start_time BETWEEN UNIX_TIMESTAMP('2026-09-01')*1000
                     AND UNIX_TIMESTAMP('2026-09-30 23:59:59')*1000;
```

## 3. 数据批量导入

### 3.1 CSV 导入（MySQL `LOAD DATA`，最快）

```sql
-- ① 建临时过渡表（列与 CSV 对齐，全 varchar 防脏数据直接报错）
CREATE TEMPORARY TABLE tmp_users (phone VARCHAR(20), nickname VARCHAR(64), role VARCHAR(20));

-- ② 导入（Windows 路径用正斜杠；LOCAL 需客户端允许 local_infile）
LOAD DATA LOCAL INFILE 'D:/import/users.csv'
INTO TABLE tmp_users
CHARACTER SET utf8mb4
FIELDS TERMINATED BY ',' ENCLOSED BY '"' LINES TERMINATED BY '\n'
IGNORE 1 LINES;   -- 跳过表头

-- ③ 过渡表 → 正式表（密码给默认哈希，首次登录后改）
INSERT INTO users (id, phone, password, nickname, role, created_at)
SELECT CONCAT('u_imp_', LPAD(ROW_NUMBER() OVER (), 6, '0')),
       phone, '$2a$10$默认哈希', nickname, IFNULL(role, 'USER'),
       UNIX_TIMESTAMP()*1000
FROM tmp_users
WHERE phone REGEXP '^1[0-9]{10}$';   -- ④ 边导入边校验：手机号格式不对的直接进不来
```

### 3.2 JSON 轨迹导入（Python 脚本，走接口最安全）

轨迹数据结构复杂（主表 + points_json + 点表三方一致），**强烈建议走同步接口**而非直插 SQL，
接口会自动做字段校验与双写：

```python
# scripts/import_trajectories.py 骨架
import json, urllib.request

BASE = "http://127.0.0.1:3000/api/v1"
TOKEN = "登录后拿到的 token"

for f in ["walk_0901.json", "walk_0902.json"]:
    data = json.load(open(f, encoding="utf-8"))
    req = urllib.request.Request(
        f"{BASE}/trajectory/sync", method="POST",
        data=json.dumps({"trajectory": data}).encode(),
        headers={"Content-Type": "application/json",
                 "Authorization": f"Bearer {TOKEN}"})
    print(f, urllib.request.urlopen(req).read().decode())
```

## 5. 数据删除（按场景）

### 5.1 删单条轨迹（先点表后主表，一个事务）

```sql
START TRANSACTION;
DELETE FROM trajectory_points WHERE trajectory_id = 'demo_001';
DELETE FROM trajectories      WHERE id = 'demo_001';
COMMIT;
-- 确认无误再 COMMIT；不对就 ROLLBACK
```

### 5.2 删某用户的全部轨迹（注销场景）

```sql
START TRANSACTION;
DELETE p FROM trajectory_points p
  JOIN trajectories t ON p.trajectory_id = t.id
  WHERE t.user_id = 'u_xxx';        -- JOIN 删除：先清点表
DELETE FROM trajectories WHERE user_id = 'u_xxx';
DELETE FROM users         WHERE id = 'u_xxx';
COMMIT;
```

### 5.3 清空测试数据（保留表结构）

```sql
TRUNCATE TABLE trajectory_points;   -- 快，自增复位，不可回滚，仅测试库用
TRUNCATE TABLE trajectories;
```

> 生产库永远不要 TRUNCATE；大表删除用「批量 + 限速」：
> ```sql
> DELETE FROM trajectory_points WHERE trajectory_id IN (旧轨迹id集) LIMIT 5000;
> -- 循环执行直到影响行数为 0，避免长事务锁表
> ```

## 6. 脏数据清理（实战脚本）

### 6.1 先摸底：脏在哪

```sql
-- 孤儿 GPS 点（主表已无对应轨迹，多由「跳过主表直接删」造成）
SELECT COUNT(*) FROM trajectory_points p
LEFT JOIN trajectories t ON p.trajectory_id = t.id
WHERE t.id IS NULL;

-- 0 点轨迹（pts 键名传错时期的遗留：points_json 只有 '[]'）
SELECT id, user_id, FROM_UNIXTIME(start_time/1000) FROM trajectories
WHERE JSON_LENGTH(points_json) = 0;

-- 单位异常：distance 明显不合理（>100km 的步行轨迹）
SELECT id, ROUND(distance/1000,1) AS km FROM trajectories WHERE distance > 100000;

-- 时间倒挂：结束早于开始
SELECT id FROM trajectories WHERE end_time < start_time;

-- 手机号脏号
SELECT * FROM users WHERE phone NOT REGEXP '^1[0-9]{10}$';
```

### 6.2 清孤儿点

```sql
START TRANSACTION;
DELETE p FROM trajectory_points p
LEFT JOIN trajectories t ON p.trajectory_id = t.id
WHERE t.id IS NULL;
SELECT ROW_COUNT();   -- 看删了多少
COMMIT;
```

### 6.3 删 0 点轨迹（连同点表，防孤儿）

```sql
START TRANSACTION;
DELETE p FROM trajectory_points p
  JOIN trajectories t ON p.trajectory_id = t.id
  WHERE JSON_LENGTH(t.points_json) = 0;
DELETE FROM trajectories WHERE JSON_LENGTH(points_json) = 0;
COMMIT;
```

### 6.4 删重复数据

```sql
-- 找重复：同一用户同一开始时间的多条轨迹
SELECT user_id, start_time, COUNT(*) c, GROUP_CONCAT(id) AS ids
FROM trajectories GROUP BY user_id, start_time HAVING c > 1;

-- 删重复（保留每组最早入库的一条；MySQL 8 支持窗口函数）
DELETE t FROM trajectories t
JOIN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY user_id, start_time ORDER BY synced_at) rn
    FROM trajectories
  ) x WHERE x.rn > 1
) dup ON t.id = dup.id;
-- 别忘了清这些被删轨迹的点表（先按 6.2 的孤儿点脚本兜一遍）
```

## 7. 数据清洗（UPDATE 实战）

```sql
-- 规范化 city：去首尾空格、统一「市」后缀
UPDATE trajectories SET city = TRIM(city) WHERE city LIKE ' %' OR city LIKE '% ';

-- 修正 avg_speed 缺失：distance(米)/duration(秒)*3.6 = km/h
UPDATE trajectories
SET avg_speed = ROUND(distance / duration * 3.6, 2)
WHERE (avg_speed IS NULL OR avg_speed = 0) AND duration > 0;

-- 时间倒挂修正：end_time 用 start + duration 兜底
UPDATE trajectories SET end_time = start_time + duration * 1000
WHERE end_time < start_time;

-- 标题去 emoji/空串（按需）
UPDATE trajectories SET title = NULL WHERE TRIM(title) = '';

-- 批量修字符串必须带 LIMIT 分批 + 逐批确认（大表防长事务）：
UPDATE trajectories SET city = TRIM(city)
WHERE city LIKE ' %' LIMIT 5000;   -- Rows matched 是总数，分批跑到 0
```

**清洗三件套（每次都做）**：

```sql
-- ① 洗前备份受影响行
CREATE TABLE bak_traj_city_20260910 AS
SELECT id, city FROM trajectories WHERE city LIKE ' %' OR city LIKE '% ';

-- ② 清洗（上面语句）
-- ③ 洗后核对
SELECT COUNT(*) FROM bak_traj_city_20260910 b JOIN trajectories t USING (id) WHERE t.city = b.city;
-- 0 行=全部改过；抽查几行确认合理后，观察一周再 DROP TABLE bak_...
```

## 8. H2 与 MySQL 方言差异（双库开发必看）

| 操作 | MySQL | H2（本项目的兼容模式） |
|---|---|---|
| 当前毫秒 | `UNIX_TIMESTAMP()*1000` | 实测兼容；也可 `DATEDIFF(...)` 复杂写法，建议统一用 SQL 外的程序生成 |
| 删了再插自增 | `TRUNCATE` 复位 | 兼容 `TRUNCATE TABLE` |
| 窗口函数 | `ROW_NUMBER() OVER (...)` | 2.x 支持，写法相同 |
| 备份恢复 | `mysqldump` / `SOURCE file.sql` | 停应用拷 `data/*.mv.db`，或 `RUNSCRIPT FROM 'file.sql'` |
| 只读分析 | 正常连 | **必须停应用**再开 Shell（文件锁独占） |
| JSON 函数 | `JSON_LENGTH` 等 | H2 2.x 支持大部分；复杂的先在 H2 Shell 试跑 |

## 9. 运维巡检（每周跑一遍）

```sql
-- 库/表体积
SELECT table_name,
       ROUND(data_length/1024/1024,1) AS 数据MB,
       ROUND(index_length/1024/1024,1) AS 索引MB,
       table_rows
FROM information_schema.tables WHERE table_schema='microtrip';

-- 数据健康五连
SELECT (SELECT COUNT(*) FROM users) AS 用户,
       (SELECT COUNT(*) FROM trajectories) AS 轨迹,
       (SELECT COUNT(*) FROM trajectory_points) AS 点,
       (SELECT COUNT(*) FROM trajectory_points p LEFT JOIN trajectories t
          ON p.trajectory_id=t.id WHERE t.id IS NULL) AS 孤儿点,
       (SELECT COUNT(*) FROM trajectories WHERE JSON_LENGTH(points_json)=0) AS 零点轨迹;

-- 慢查询开关（排查期临时开）
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;    -- 秒
```

## 10. 安全规范（一条都不能省）

1. **UPDATE/DELETE 前必跑同条件 SELECT**，确认影响行数与预期一致；
2. **写操作包事务**（`START TRANSACTION ... ROLLBACK/COMMIT`），生产环境先用只读账号预演；
3. **先备份**：改数据前 `mysqldump` 单表，或 `CREATE TABLE bak_xxx AS SELECT ...` 存原值；
4. 禁止无 WHERE 的 UPDATE/DELETE（客户端开 `--safe-updates` 兜底：`mysql -U`）；
5. 大表删除/更新**分批 LIMIT**，观察锁与主从延迟；
6. 密码字段只存 BCrypt 哈希；任何导出文件含用户数据都要走脱敏（`CONCAT(LEFT(phone,3),'****',RIGHT(phone,4))`）；
7. 生产库连 `points_json` 大字段列表查询都别碰 `SELECT *`（应用层已是投影查询，SQL 手工查同理）。
